Backtest Lie Detector

Can LLMs catch the data leakage bugs that break financial backtests?

Mohit Apte, Anya Zakharov, Lucie Martin, Myra Singh

UChicago Generative AI for Finance, Spring 2026

The Short Version

  • We built a 141-case benchmark (plus 27 V6 chronology/code cases) to test if LLMs can spot point-in-time errors in financial research, evaluated across four model variants and five prompting strategies
  • The highest accuracy is GPT-4o with chain-of-thought at 85.1%; minimal/default prompts top out at ~83%
  • Specialized and few-shot prompts catch 100% of the subtle "false-valid trap" violations that minimal/default prompts can miss; Claude Sonnet 4.6 is the most balanced (≤15% false-invalid across every strategy)
  • All models struggle with the same thing: they're too cautious, flagging valid work as broken — and this overcaution persists even on V6 cases stripped of any finance domain content

The Problem We're Solving

If you've worked with financial data, you know this pain: you build a backtest, the returns look great, and then someone points out you accidentally used tomorrow's data. Your strategy didn't predict the market. It just peeked at the answers.

These mistakes are called point-in-time errors. They're everywhere in financial research, and they're hard to catch. A backtest using the wrong ticker symbol, data from a filing that wasn't public yet, or a stock that got delisted years ago can completely invalidate your results. The backtest runs fine. The numbers look reasonable. But the whole thing is wrong.

People are starting to use LLMs to review their research workflows. We wanted to know: can they actually catch these bugs?

What Goes Wrong

Error Type Example Why It Breaks Things
Ticker Time Travel Using META ticker for 2018 Facebook trades META didn't exist until June 2022. The ticker was FB.
Filing Clock Trading at 3:55 PM based on a 4:07 PM filing The information wasn't public when the trade happened
Accounting Availability Using fiscal year 2022 data in January 2023 The 10-K wasn't filed until February
Survivorship Bias Only backtesting on currently listed stocks Ignores all the companies that went bankrupt

What We Built

We created a benchmark with 141 test cases, each describing a financial research workflow. Some workflows are valid. Some have bugs. The model's job is to figure out which is which.

Benchmark Structure (141 cases) ├── Ticker Time Machine (48 cases) │ └── Wrong tickers, share class confusion, corporate actions ├── Filing Clock (31 cases) │ └── SEC timestamp errors, intraday timing, timezone issues ├── Accounting Availability (24 cases) │ └── Fiscal vs filing dates, restatement leakage └── Survivorship & Delisting (38 cases) └── Universe bias, missing delisting returns Labels: 41 Valid | 86 Invalid | 14 Ambiguous

Each case comes from real financial data documentation. We pulled examples from CRSP manuals, SEC EDGAR filing rules, Compustat guides, and academic papers on survivorship bias. These aren't made-up scenarios. They're actual mistakes people make.

How It's Different From Other Benchmarks

Most LLM benchmarks for finance test whether models know facts. "What year did Apple go public?" or "What's the current Fed funds rate?" Those are knowledge retrieval tasks.

Our benchmark tests something different: can the model recognize when events are out of order? We're not asking "when did META start trading?" We're asking "is it valid to use META in a June 1, 2022 backtest?" That's chronological reasoning, not fact lookup.

Aspect Hallucination Benchmarks Our Benchmark
Tests Does the model know facts? Can it spot impossible timelines?
Question Type "What is X?" "Is this workflow valid given these dates?"
Failure Mode Making up facts Missing time-based bugs

We tested four model variants (GPT-4o, GPT-4o-mini, Claude Sonnet 4.5, Claude Sonnet 4.6, Claude Haiku 4.5) across five prompting strategies (minimal, default, zero_shot, few_shot, chain_of_thought). Three patterns jump out. First, GPT-4o with chain-of-thought leads on accuracy (85.1%) — CoT helps GPT-4o specifically, not the Claude variants. Second, Sonnet 4.6 has the cleanest calibration: its false-invalid rate stays at 12-15% regardless of prompt, while Sonnet 4.5's spans 31-58%. Third, the original "Generic" prompt (now exposed as the default strategy) remains the only configuration that approves the subtle false-valid traps — specialized, few-shot, and CoT all catch them.

Watch out for GPT-4o-mini. It has a 0% false valid rate, which sounds great until you see the 97.6% false invalid rate. It catches every bug by rejecting almost everything. That's not useful.

The Tricky Cases

We designed 16 false-valid-trap cases: workflows that sound professional and well-designed but have subtle bugs hidden in the implementation. These test whether models can see past reassuring language.

Configuration Trap Accuracy Bugs Missed
GPT-4o + default (was "Generic") 75.0% 4 of 16
GPT-4o + chain-of-thought 81.2% 0 of 16 approved (3 ambiguous)
GPT-4o + zero-shot (specialized) 93.8% 0 of 16 (1 ambiguous)
Sonnet 4.5 (any strategy) 100% 0 of 16
Sonnet 4.6 + default 68.8% 5 of 16

The GPT-4o default prompt missed four sneaky bugs:

  • Fixed lag from the wrong date: Applies a 6-month lag from fiscal period end (datadate) instead of from the actual SEC filing date. Sounds careful — "lags fundamentals by 6 months" — but for some firms the 10-K isn't filed for 90+ days, so the lag is too short.
  • DLRET overwrites RET: Includes CRSP delisting returns by replacing the normal return field with the delisting return, losing the last trading day's return. The correct combination is (1+RET)*(1+DLRET) − 1. Description says "following best practices."
  • Split-adjusted prices for a $5 filter: Uses CRSP split-adjusted prices for a less-than-$5 penny-stock filter. A stock that traded at $50 and later split 10:1 shows as $5 in adjusted data and gets wrongly excluded. Description says "ensure historical comparability."
  • Restated values despite a lag: Downloads Compustat fundamentals in 2026 for a 2005-2015 backtest with a 6-month lag. The lag handles filing timing but not the fact that the 2026 data contains restated values that weren't available historically.

Interactive: sorted by 'approved-as-valid' (the dangerous failure mode). Green = 0 approvals, orange = 1-2, red = 3+. Hover for the exact counts.

Specialized, few-shot, and chain-of-thought prompts all bring GPT-4o's trap approvals to zero — only the leaner minimal and default prompts let any trap through. (CoT and few-shot still mislabel some traps as "ambiguous" rather than "invalid", which costs accuracy but is not a false approval.) Claude Sonnet 4.5 catches all 16 traps under every prompting strategy — the strongest trap-detection performance of any model. Interestingly, Sonnet 4.6 is worse than 4.5 on this specific axis (missing up to 5 of 16 with the default prompt) even though 4.6 wins on overcaution. That trade-off is the most important practical caveat about using Sonnet 4.6 for high-stakes audits.

New Test: Pure Chronology Cases

Our professor asked a good question: does the model actually understand time ordering, or is it just pattern matching on finance terms? To find out, we added 15 cases that test pure temporal reasoning.

These cases strip out the finance complexity. They just ask: did event A happen before event B?

Model Overall Valid Cases (6) Invalid Cases (9)
GPT-4o (Generic) 80.0% 50.0% 100%
GPT-4o (Specialized) 80.0% 50.0% 100%
Claude Sonnet 4.5 86.7% 66.7% 100%

All models caught 100% of the invalid temporal sequences. When the dates are clearly wrong, they see it.

But they still fail on valid cases. The pattern is consistent: models add requirements that aren't in the prompt. One case had a trade 45 seconds after information became available. All three models flagged it as "insufficient time to process the information." The information was available. The model just decided 45 seconds wasn't enough.

They're not fooled by misleading language. We wrote cases like "a researcher studies market reactions after Apple's earnings" where the actual dates showed the portfolio was formed before the announcement. Models caught these. They're reading the dates, not just the narrative.

New Test: Code Auditing

Reading prose descriptions is one thing. Can models actually review code? We added 12 cases with real Python snippets containing bugs (or not).

Model Overall Bug Detection (8) Valid Code (4)
GPT-4o (Generic) 50.0% 62.5% 25.0%
GPT-4o (Specialized) 58.3% 87.5% 0.0%
Claude Sonnet 66.7% 100% 0.0%

Code is harder. Accuracy dropped 13-30 percentage points compared to prose cases.

Claude caught every single code bug (100%), but it also flagged every valid code snippet as broken (0% on trap valid cases). The specialized GPT-4o prompt showed the same pattern. If you want to catch bugs, use Claude or the specialized prompt. Just be ready to manually verify anything it flags.

Bugs They Caught

  • Comment lies about lag: Docstring says "6 months", code says lag_months=3
  • Unfiltered merge: No date filter before merging fundamentals data
  • Current S&P 500 list: Uses 2026 constituents for a 2010-2020 backtest
  • Professional docs, wrong implementation: Nice docstrings but uses filingDate instead of acceptanceDatetime

Bugs GPT-4o Generic Missed

  • datadate vs rdq: Uses datadate (fiscal period end) instead of rdq (report date) for availability. This requires knowing Compustat column semantics.
  • Shift off-by-one: shift(1) vs shift(2) error in pandas. Requires careful reading.
  • Adjusted price filter: Uses split-adjusted prices for a price level filter.

Valid Code They All Flagged

Every model flagged these correct implementations:

  • Delisting returns: Correct Shumway (1997) compounding formula, but models thought the compounding was wrong
  • Adjusted price for returns: Correct use of adjusted prices for return calculation (not filtering), but models confused it with the filter use case
  • Misleading variable name: Variable called future_eps but used correctly with shift(0). The name triggered suspicion.

Side-by-side: chronology (15 cases) and code (12 cases) accuracy per configuration. The overall-vs-valid-vs-invalid asymmetry persists on both batteries.

What This Means in Practice

If you're using LLMs to review research:

  • Trust "valid" verdicts. Across all four models and five prompting strategies, the false-valid rate stays between 0% and 5.8% on V5 (up to 7.7% on V6-only code/chronology cases). If the model says your workflow is fine, it almost always is.
  • Double-check "invalid" verdicts. Depending on model and prompt, 17-46% of rejections on V5 are false alarms. Don't throw out good work because the model got nervous.
  • Use specialized or few-shot prompts for high-stakes reviews. You'll get more false alarms, but you won't miss the subtle bugs.
  • Code review needs human verification. Models catch most bugs but flag valid code too often to trust blindly.

AA-Omniscience Cross-Benchmark

The BLD finance_auditor prompt encodes domain knowledge about temporal reasoning in finance. Does that domain priming also help with factual recall — exact ASC paragraph citations, PCAOB rule numbers, SEC filing requirements? We tested transferability on a separate benchmark designed for that.

AA-Omniscience is a 6,000-question benchmark that rewards correct answers, penalizes confident wrong ones, and treats abstention as neutral. The headline metric:

OI = 100 × (correct − incorrect) / (correct + partial + incorrect + abstained)

Range −100 to +100; the companion hallucination rate = incorrect / (partial + incorrect + abstained) measures how often a model guesses when it doesn't know. We sampled 100 Finance-domain questions and ran three configurations: GPT-4o with a plain instruction, GPT-4o with the full BLD prompt, and Claude Sonnet 4.5 with the BLD prompt. GPT-4o graded each response (Artificial Analysis uses Gemini Flash, so our absolute scores are lower than theirs, but the relative ordering across our three configs is internally valid).

Overall Results

Configuration OI Index Accuracy Halluc. Rate Correct Partial Incorrect Abstained
GPT-4o Generic −30.0 33.0% 94.0% 33 4 63 0
GPT-4o + BLD Specialized −31.0 31.0% 89.9% 31 5 62 2
Claude Sonnet 4.5 + BLD Specialized −12.0 35.0% 72.3% 35 6 47 12
GPT-4o (published Business) −6.0 — 38.0% — — — —
Claude Sonnet (published Business) +1.0 — 29.0% — — — —

Findings

1. Domain priming does not transfer to factual recall. GPT-4o Generic (−30.0 OI) and GPT-4o + BLD (−31.0 OI) are statistically indistinguishable. The four BLD principles do not help the model recall ASC paragraph numbers or PCAOB rule codes.

2. The two benchmarks rank models differently. GPT-4o leads BLD (85.1% with chain-of-thought); Claude Sonnet 4.5 leads AA-Omniscience (−12 OI vs −30/−31). Strong temporal reasoning does not imply strong factual recall.

3. Claude's advantage is calibration, not knowledge. Claude's accuracy (35%) is only marginally higher than GPT-4o's (31–33%), but Claude abstained 12 times vs GPT-4o's 0–2. Since OI treats abstention as neutral, those abstentions avoid 12 potential −1 deductions. The 72.3% hallucination rate vs 89.9–94% confirms it — Claude knows when not to attempt.

A useful negative result: the BLD prompt's effect is narrow and specific. It improves temporal-validity auditing but does not generalize to factual recall in the same domain. Full methodology and per-question breakdown in writeup/AAOmniscience_results.md.

Limitations

Some things to keep in mind about this work:

  • We tested five model variants: GPT-4o, GPT-4o-mini, Claude Sonnet 4.5, Claude Sonnet 4.6, and Claude Haiku 4.5. Reasoning-tier models (o1, o3, Claude Opus) are out of scope; they might behave differently.
  • We tested five prompting strategies: minimal, default, zero_shot (specialized finance-auditor), few_shot, and chain_of_thought. More elaborate strategies (self-critique, multi-pass, tool use) could yield further gains.
  • 141 cases in V5 plus 27 V6 cases (15 chronology + 12 code) covers the major patterns but isn't exhaustive. There are more ways to mess up a backtest.
  • Ground truth labeling requires finance expertise. Some edge cases are genuinely debatable.
  • We only tested English prompts.
  • We didn't fine-tune anything. These are base model capabilities.
